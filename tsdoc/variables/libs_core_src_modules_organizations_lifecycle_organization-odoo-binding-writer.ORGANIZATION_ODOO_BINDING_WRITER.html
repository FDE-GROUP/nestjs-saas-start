    租户↔Odoo 绑定状态推进写入端口（module-org-odoo-company-mapping 切片 C · §9.5.4①B 端口倒置）。

    Remarks

    消费方 = features/odoo-provisioning（开通 saga：先落意图→建司→回写/失败）。features 禁 import 其他上下文的 domain/infrastructure（features 隔离铁则），而绑定事实的持久化住 organizations 上下文， 故写端口与 ORGANIZATION_ODOO_BINDING_READER 同法居 @core（published port·沿 ROLE_ASSIGNABILITY_READER 先例），适配由 apps 装配根绑定（organizations 基础设施 Mikro 写面·MikroOrganizationGovernanceRepository）。

    saga 的持久化状态机被拆成本端口三原子动作（每步各自耐久·崩溃可由「先落意图 + 命名回找」恢复）：

    • OrganizationOdooBindingWriter.beginProvisioning：审批事件领取即落 provisioning（意图持久化· pending→provisioning，或失败重试重入），令「方向永远对」——孤儿公司降为低频审计项（§1 单源裁决）；
    • OrganizationOdooBindingWriter.markReady：建司/本地化/预配全绿后回写 ready + 公司 id/名快照 + boundAt，清失败原因（Odoo 能力唯一放行态·canUseOdoo 前置）；
    • OrganizationOdooBindingWriter.markFailed：任一步失败置 failed + 携原因（doctor/saga 重试承接）。

    本端口不校验公司在 Odoo 侧存在性（跨库弱引用·正向核验归 doctor），只守 SaaS 侧映射行的状态/快照写入。
