模块按 Clean Architecture 分层：
- `api/`：Nest 对外暴露面——`oauth-sso.controller.ts` 作为 SSO OP 端点；`guards/session.guard.ts` 注册为全局 `APP_GUARD` 实现 deny-by-default 会话墙，`csrf-origin.guard.ts` 在其后做 CSRF Origin/Referer 校验；`decorators/current-user.decorator.ts` 从请求提取已认证主体。
- `application/ports/`：面向应用层的抽象端口（如 `mcp-access-token-store.port.ts`、`mcp-token-verifier.port.ts`），被上层 features 通过 DI token 注入，auth 域不反向依赖调用方。
- `domain/ports/`：领域级持久化契约（`session-store.port.ts`、`user-store.port.ts`），以 Symbol 常量（`AUTH_SESSION_STORE`、`AUTH_USER_STORE`）作为 DI token，供治理侧受控写 session 表。
- `infrastructure/`：better-auth 的具体装配——`auth.implement.ts` 中 `CreateAuth()` 构造 BetterAuth 实例并封装 `handler` + `auth.api.*` 窄门面（封堵 BA org HTTP 面、透传服务端编排 API）；`auth.bootstrap.ts` 在 `OnApplicationBootstrap` 阶段把 handler 挂到 Fastify 实例级通配路由 `/api/v1/auth/*`；其余 adapter/service（`session-store.adapter.ts`、`user-store.adapter.ts`、`mcp-access-token-store.adapter.ts`、`oauth-sso.service.ts`、`sso-token.service.ts`、`session-reclaim.service.ts`、`generic-oauth-channels.ts`、`social-provider-registration.ts`）分别对接 MikroORM、Mailer、ConfigService。
- 顶层 `auth.module.ts` 通过静态 `forRoot()` 返回 `DynamicModule`，集中装配 providers、exports 全局守卫与端口适配器，并声明 `global: true`；`auth.interface.ts` 导出 `AuthInstance` 类型，由 `AuthInstanceInjectKey` 在模块内循环引用。
依赖方向单向向外：infra → domain/application ports ← api guards/controllers，外部 feature 仅消费 exports 中的 guard、token 与 auth instance getter。
